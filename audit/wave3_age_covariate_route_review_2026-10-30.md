# Wave 3 age and covariate routing review (2026-10-30)

## Scope

This is a preparation and restricted aggregate-QA note for the CHARLS 2015 Sample_Infor/Blood frame. The protected audit processes pseudonymous IDs only in memory to reconcile the official Demographic_Background module to the Sample_Infor frame; it emits no IDs or exact dates and writes only aggregate QA under the private root. It reads no exposure or blood-outcome fields for the age-route audit, derives no respondent ages, selects no analytic domain, and authorizes no association model.

## Official field map

The 2015 Codebook describes the Sample Information module as the released sample frame and lists `ID`, `householdID`, `communityID`, `crosssection`, `died`, `iyear`, and `imonth`. `crosssection` identifies the cross-sectional sample. `iyear` and `imonth` are string interview-timing fields; they provide year and month, not interview day.

The Codebook's Demographic Background section lists:

- `ba004_w3` and components `ba004_w3_1`–`ba004_w3_3`: birth date on the respondent's ID card or household registration (year/month/day).
- `ba002` and components `ba002_1`–`ba002_3`: the questionnaire asks whether actual birth date is the same as the civil-document date (`1`) or a separate reported date (`2`); only route 2 supplies the separate date components.
- `ba003`: whether the date response uses the solar (`1`) or lunar (`2`) calendar. The questionnaire order and Codebook frequencies suggest BA003 is primarily applicable to the separate actual-date route (`ba002=2`), while `ba002=1` uses the civil-document date. A private route-by-calendar cross-tab nevertheless found some BA003 values on BA002=1 and missing/unrecognized BA003 values on a subset of BA002=2. The audit requires calendar data for BA002=2 and records both patterns; it does not use BA003 values on BA002=1 to infer a calendar, nor treat unasked values there as required. The questionnaire also says to skip BA003 when the respondent does not know the date (`ba002=.d` or `.r`). Route applicability and these discordant cases remain for independent methods review.

These fields are in a different module from Sample_Infor. Therefore the frame-first preparation may retain a sampled person whose demographic row is absent; the age inputs for that person must remain missing. Do not infer eligibility, spouse status, or age from household rosters, adjacent waves, interview status, or ID patterns.

## Safe derivation sequence to review before implementation

1. Preserve Sample_Infor as the Wave 3 frame and `crosssection` as the published domain flag. Establish the blood-weight target separately from age derivation; do not substitute `INDV_weight_ad2` or a later-wave weight.
2. Apply the questionnaire route: `ba002=1` means the actual date matches the ID/household-register date, so the source date is `ba004_w3_*`; `ba002=2` supplies a separate actual date in `ba002_*`. Require `ba003` only for the separate actual-date route (`ba002=2`); do not treat its absence on the same-as-document route as missingness. The questionnaire skips `ba003` when the respondent does not know the birth date (`ba002=.d` or `.r`). Retain route and calendar status; do not silently substitute the other date source.
3. Validate the month/day codes, partial dates, invalid calendar dates, missing route responses, and agreement/disagreement between the two reported dates using official labels and questionnaire instructions. Never infer a missing month/day as January or mid-month.
4. Convert lunar dates only with the pinned CHARLS-maintained `lunar2solar` mapping. A source-only parser has compared every row in the official ordinary and leap `.mmat` tables with pinned Python 0.1.4 and found zero differences. This closes mapping parity; Wave 3 route handling, interval construction, and independent age review remain open. The optional Stata workflow is no longer a prerequisite.
5. Because the interview source has year/month but no day, calculate a conservative age interval from the valid birth-date route rather than a falsely exact age. Keep unresolved, incomplete, or contradictory records unclassified. Any threshold/domain assignment must be stable across the interval or remain unresolved.
6. Freeze the target population and age-domain rule with the blood-response weight, cross-sectional flag, and survey design before building complete-case models. Define covariate adjustment from the estimand/DAG, not from whichever columns happen to be present. Report module-specific missingness in private QA and retain missingness rather than imputing from other modules.

The questionnaire instructs interviewers to record month/day as `0` when unknown and gives 1900–2015 as the birth-year range. The private audit therefore treats zero month/day as unknown, never as January or the first day.
## Current gate

The Wave 3 frame-to-Blood join has passed protected ID-only linkage and weight-domain checks. On 2026-10-30, the source-bound preparation was repeated locally from the official All Data archive into a separate protected output directory, then joined to the official Blood artifact. Both archive hashes matched the pinned CHARLS release values, the `Sample_Infor` spine and output hashes were bound in the private manifest, and the one-to-one left merge retained the released frame. A hash-bound private aggregate audit confirms the required age-source fields and interview timing are present. It also reconciled the prepared Sample_Infor frame against IDs from the official Demographic_Background module, without emitting IDs: prepared BA002 routes exactly matched the official module for linked records, and the audit now separates records without a demographic-module row from item-level BA002 missingness in records that do have such a row. This matters because the official frame is broader than the demographic module. The first age audit incorrectly required BA003 for both BA002 routes. Review of the official questionnaire sequence and Codebook frequencies suggested BA003 is primarily applicable to the separate actual-date route (BA002=2), so the private audit was corrected to require it on that route only. A private route-by-calendar cross-tab found BA003 values on some BA002=1 records and missing/unrecognized BA003 values on some BA002=2 records. These discordant cases are recorded for methods review; the source file does not preserve user-missing distinctions in the audited route field, so the questionnaire's `.d`/`.r` skips cannot be assigned from system-missing values alone. No exact counts or participant-level data are in this repository. The audit also flags zero month/day inputs (explicitly treated as unknown), missing date components, and no date components outside documented numeric ranges. The private audit does not establish valid ages or an analytic domain. Age intervals, route/code adjudication, covariate completeness, blood-weight target, PSU/variance, estimand freeze, and independent methods review remain open. Formal association models remain zero.
